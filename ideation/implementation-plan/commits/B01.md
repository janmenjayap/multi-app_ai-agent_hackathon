# B01 — Persist authoritative application state and evidence atomically

**Branch:** [feat/durable-core](../branches/feat-durable-core.md) · **Owner:** P1.
**Suggested commit subject:** `feat(B01): persist app transitions with events and jobs`
**Hard prerequisite:** [F02](F02.md).
**Scope source:** [canonical B01 backlog](../04-commit-plan.md).

## Purpose and current state

**Application persistence is not implemented.** The existing
[MonitorStore](../../../src/server/storage/monitor-store.ts) atomically persists
supplied observations plus measurement jobs and preserves attempts, evidence,
labels, assessments, lease fencing, and exhaustion. It does not persist application
runs/effects or make business transitions atomic with monitoring.

This commit must put the application transition, canonical event, and corresponding
measurement job in **one transaction on the same application SQLite database and
connection**. A later call to `MonitorStore.append()` on a separate file is insufficient.

## Sequential implementation

1. Inventory existing monitor tables, `user_version`, keys, and fixture databases.
   Plan a migration preserving their data; distinguish business runs/effect attempts
   from monitor evaluation attempts. Do not overwrite the monitor's schema version.
2. Add the application run/snapshot/plan/approval/effect/attempt and verification
   repositories with unique identities, foreign keys, restricted payload storage,
   and short explicit transactions.
3. Refactor connection/transaction ownership so application repository changes and
   canonical event/job insertion share one transaction. Expose a transaction-scoped
   writer without nested independent BEGIN/COMMIT operations. Preserve the CLI's
   standalone store path; graph checkpoints remain a separate store.
4. Persist dispatch intent and attempt mappings, and emit sanitized events/job
   identities. Storage failure must return failure before callers can dispatch.
   Preserve original proposal/effect history and current measurement exhaustion.
5. Add migration, interrupted-transaction, uniqueness, reopen, and privacy tests
   in this commit. Force failure between state, event, and job inserts and prove
   either all survive or none do, including a terminal transition.
6. Run application storage tests and existing monitor regressions; reopen a real
   file and inspect restored records before handing repositories to B04/B05/B06/B07.

## Reliability records and atomicity acceptance

The [detailed reliability plan](../06-agent-reliability-implementation.md) extends this transaction boundary to real execution evidence.

1. Persist immutable source snapshots/versions, raw original model output references/digests, model/tool attempts, exact request intent, authenticated approval receipts, verification observations and success-claim records. Retain ordered correction/review-label revisions instead of replacing first outputs.
2. Allocate event sequence and causal references in the transaction that changes application state. Every durable transition, including waiting, blocked, failed, failed_partial, completed and stalled, inserts its canonical event and assessment job on the same connection. One later monitor append cannot repair missing atomic evidence.
3. Store boot/process identity with monotonic elapsed values and UTC bounds. Across restarts, use durable event/causal order; never subtract unrelated process clocks. A claim must reference the verification scope available when it was emitted.
4. Expose a restricted evidence writer/reader and transaction-scoped append API to A01, I01 hooks, B04–B07 and Q03. Provider transport hooks are injected by integration; adapters do not open a competing SQLite database.
5. Preserve v1 assessments and raw observations during the planned evaluator-version migration. New evidence or label revisions schedule reassessment while keeping evaluation-attempt denominators stable.

**Additional acceptance:** kill/reopen around intent persistence, model-result persistence, terminal state and job insertion; either the full local transaction survives or none does. A failed predispatch receipt prevents the call. An interrupted in-flight call remains unresolved, never fabricated as success or nonapplication. Hand Q03 migration/rollback receipts and an event/job cursor spanning restart.

## Agent, LLM and external-app integration

Use the [LLM call guide](../07-agent-spawning-and-llm-integration.md) and
[app transport guide](../08-mcp-api-and-external-app-integration.md) with the
[F02 handoff contract](../05-contracts-and-handoffs.md). This commit owns:

- `storage/repositories.ts` persists role invocation claims, frozen input/model/prompt/schema digests, attempt starts and immutable raw artifacts consumed by A01. Atomic compare-and-claim prevents concurrent role dispatch; validated results remain reusable across B04 restarts without resetting budgets. Store unresolved calls honestly; do not promise exactly-once LLM usage.
- Persist app/account/transport identity, request hashes and separate provider attempts for I01–I05/B06. The business effect key stays the same across retries; an unknown REST/MCP outcome cannot release it for a new create. Keep raw model/provider content restricted and secrets absent.
- Storage tests cover successful role result reuse, first malformed output retention, interrupted model dispatch, and unknown app writes. This commit implements persistence only; A01 and adapters own outbound traffic.

## Do not

- Claim atomicity across separate application and monitoring files or across
  SQLite and provider API calls.
- Hold a transaction across network/model operations, discard raw attempts, or
  turn failed audit persistence into permission to execute.
- Migrate by deleting evidence/history or count job retries as new evaluation attempts.

## Purpose and current state

**PLANNED.** The existing offline checker compares caller-supplied snapshots,
and the monitor evaluates supplied readback events. Neither performs independent
provider reads. Implement the product's inline read-only verifier and cautious
Slack finalization against the frozen exact plan.

## Allowed paths

`src/server/verification/readback.ts`, `src/server/verification/assertions.ts`,
`src/server/verification/finalize.ts`;
`tests/app/verification.test.ts`. Consume adapter read capabilities and B01
verification repositories; keep evaluator/checker implementation unchanged.

## Sequential implementation

1. Define provider-read requests and expected-field comparisons for all five
   artifact kinds using F02 plan/effect contracts. Read the provider ID afresh;
   do not use the executor's create response as observed final state.
2. Check HubSpot owners/due dates/associations, GitHub incident/content/linkage,
   actual dereferenced cross-links, marker duplicates, and protected records.
   Decode all Gmail To/Cc/Bcc headers and approved subject/body normalization.
3. Persist each independent observation, timestamp, completeness, and verdict
   through B01. Bounded unavailable/missing/mismatching reads stay unverified or failed.
4. Construct Slack artifact summary only from verified effects; while its own
   readback is pending, describe coordination finalization as pending. Retrieve
   the final summary before permitting full API `completed`.
5. Add independently tampered recipient/body/owner/association/missing-record/
   duplicate/phantom-Slack fixtures in this commit. Assert failure of early
   whole-run success and failed final Slack readback.

## Inline verification, claim scope, and independent evaluation

This commit implements the product completion gate described in the [reliability plan](../06-agent-reliability-implementation.md). Q02 remains a separate non-mutating evaluation collector.

1. Keep readback/assertion clients read-only. Finalization uses the narrow guarded Slack coordination capability injected through the F02 seam and integrated by R01; sharing orchestration does not grant arbitrary writes to verifier reads.
2. Persist raw response references/digests, read start/end UTC bounds, monotonic duration, source/provider version when available, pagination completeness and scope for every observation. Distinguish a create acknowledgement, inline readback and Q02's independently collected S0/S1 evidence.
3. Bind unknown provider IDs only through unique marker/identity reads against typed logical EffectIdRef obligations. Resolve distinct ApprovedContentRef values exclusively from B03's immutable approved plan bytes/digests, frozen before dispatch; retain Q01's pre-run semantic facts for independent Q05 review. Preserve the frozen logical manifest hash, approved plan/content receipt, independent ID bindings and separate concrete export hash; never reconstruct expected content from actual records.
4. Give each success statement a stable claimId, runtimeAttemptId, emission time/causal position, exact scope and verification references. A Slack artifact-scope message may say the four business artifacts are verified while coordination finalization remains pending. The subsequent artifact-producing run completion claim requires fresh final Slack readback as well. The typed no_affected path instead verifies complete source/selection-empty and absence predicates, has no planRef, and requires no final Slack artifact.
5. Test success claims with wrong recipients, missing artifacts, stale prewrite reads, cross-run verification references, ambiguous bindings, content resolved from provider responses and unavailable final Slack reads on artifact-producing runs. Test valid no_affected with no plan/Slack requirement and invalid no_affected backed by incomplete source/absence reads. Keep failure/unverified distinct; prevent completion in every uncovered scope.

**Additional acceptance:** Q03/Q05 can distinguish premature claims from independent outcome contradictions. A later Q02 mismatch without evidence covering claim time is unverified for that claim (or documented later drift), not automatically false at emission. B07's passing inline verdict never substitutes for Q02's independent outcome or actual human semantic labels.

## Agent, LLM and external-app integration

Use the [LLM call guide](../07-agent-spawning-and-llm-integration.md) and
[app transport guide](../08-mcp-api-and-external-app-integration.md) with the
[F02 handoff contract](../05-contracts-and-handoffs.md). This commit owns:

- `verification/readback.ts` independently invokes I02 comment, I03 task/note, I05 draft and I04 message reads; `assertions.ts` compares the approved fields, full MIME recipients/body and associations. The model's answer, MCP result text or create response is not readback.
- `verification/finalize.ts` builds the final Slack summary from verified ledger entries in code, uses I04 coordination, and performs a fresh summary read before run completion. No LLM summarizes or edits approved output at this stage.
- Test absent/altered artifacts, incomplete reads, wrong accounts and phantom success for the selected transport. Q02 performs separate evaluation reads and records its own times/request IDs; it cannot copy this verifier's verdict.

## Do not

- Treat HTTP success, model confidence, tool return payload, or copied expectation
  values as independent provider evidence.
- Claim artifact-producing run completion before the final Slack summary is read back, or use the no_affected scope to bypass required artifact verification.
- Add write authority to verifier read clients or turn incomplete retrieval into pass.

## External-app integration to implement in this commit

Implement the [Slack route/token mapping](../08-mcp-api-and-external-app-integration.md#5-slack--i04)
in `src/server/adapters/slack.ts` through I01. At `https://slack.com/api/`,
`POST chat.postMessage` publishes the exact marked review;
`POST chat.update` updates the app-owned coordination message;
`GET conversations.history` finds it in the bounded configured channel; and
`GET conversations.replies` independently retrieves parent and complete replies.
Validate Slack `ok` as well as HTTP status. Preserve message/thread timestamps as
strings and authenticated actor/workspace/channel/version information.

F01 owns `PG_SLACK_BOT_TOKEN`, `PG_SLACK_READER_TOKEN`, `PG_SLACK_TEAM_ID`,
`PG_SLACK_CHANNEL_ID`, and `PG_SLACK_APPROVER_IDS`; R01 injects separate posting
and reader capabilities. The app needs `chat:write`, channel membership, and
the appropriate `channels:history` or `groups:history` grant for the proven
reader. Current docs list bot and user token support; actual channel reply-read
proof is the gate. Record any additional `users:read` needed by actor lookup.

B05 alone interprets a retrieved allowed human's reply as a decision bound to
the stored exact plan. R01's finalization path uses this adapter after effect
verification, then B07 independently reads the summary; Q02 retrieves its own
authority/finalization observations. No agent receives this adapter, and neither
approval polling nor Slack posting makes an LLM call. The polling MVP requires no
incoming webhook, Events API subscription, or model-bound MCP tool.

**Handoff gate:** owned fixtures cover denial, `ok:false`, pagination, wrong
actor/thread and edited decisions. `tools/smoke/slack.ts` must prove a real human
reply and independent post/update/readback in the exact disposable channel.
Honor actual installation rate limits; UI polling does not set Slack call cadence.

## Sequential implementation steps

1. Implement one marked thread's post/find/get/update methods using I01, retaining workspace, channel, thread, message IDs, actor type, and message edit/deletion metadata.
2. Implement complete reply pagination and provider-level success/error normalization, including Slack's ok field. Test successful HTTP responses containing failure, denied thread reads, rate limits, and duplicate marker matches.
3. Separate review and final-summary observations in attempt metadata. Preserve exact rendered content for trusted read-back while keeping general event logs redacted; add review/summary and stale-message fixtures.
4. Return reply observations to B05 without interpreting them as authorization. Add tests that bot-authored, edited, malformed, or unrelated replies survive normalization with the fields policy needs.
5. Implement tools/smoke/slack.ts for the configured disposable thread; later prove a real human reply is independently retrievable as well as posting/updating the thread. Run the owned tests and F01 build/typecheck, recording any unavailable permission explicitly.

## Slack approval and completion-claim observations

Support the [reliability plan](../06-agent-reliability-implementation.md)'s authentic approval and claim-timing requirements.

1. Retain complete thread/reply history with real workspace/channel/thread/message/actor IDs, actor type, edit/deletion metadata and read windows. Record provider errors and pagination gaps even when posting is permitted.
2. Distinguish review publication, human decision observations and final-summary changes in logical calls and receipts. All coordination writes count as tool attempts; a successful post does not establish valid approval or verified finalization.
3. Preserve the exact posted/read-back summary digest and message ID for B07's stable claimId/scope binding. A scope-limited artifact summary and a later full-completion API claim must be distinguishable in Q03's trace.
4. Expose the same normalized read interface separately to Q02; it independently retrieves approval and final-thread evidence instead of accepting B05/B07's flags.
5. Add fixtures for correct approval text in the wrong workspace/thread, edited/deleted approval after reading, a forged actor assertion, HTTP 200 with ok=false and a summary update acknowledged but absent on fresh read.

**Additional acceptance:** B05 can authenticate every authority-relevant field, B07 can prove summary readback, and Q02 can independently contradict both using actual records. Posting permission alone leaves reply/history-read gates unverified.

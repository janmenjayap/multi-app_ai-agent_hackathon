## External-app integration to implement in this commit

Use the [MCP/API integration guide](../08-mcp-api-and-external-app-integration.md)
as the concrete transport/configuration specification. Implement bounded REST
transport in the owned common files, consumed by I02–I05; R01 constructs clients
in `src/server/composition.ts`. F01 owns `.env.example` and startup validation for
`PG_ADAPTER_MODE=fake|rest` and server-private account/credential configuration.
Inject clock, transport, budgets, and receipt sinks; never read credentials inside
a model role or persist them in graph state. Stateful fakes exercise the same F02
method/results contract; REST credentials missing at startup/preflight cannot
cause a silent fake fallback.

This commit supplies read/mutation result normalization and capability-separated
plumbing. R01 source nodes use reads before B02 selection; B05 gets Slack
coordination/reads, B06 gets narrow approved mutation methods, and B07/Q02 get
separate readers. It makes **zero LLM calls**: A01 owns model invocation and
agents receive evidence projections, not provider tools.

MCP is an optional I01 follow-up at
`src/server/adapters/common/mcp-transport.ts`, with a corresponding conformance
test and F01/F02-reviewed config/dependency changes. That path is not added to
this commit's allowed paths. Before its activation, `mcp` mode is unsupported.
The follow-up must initialize/negotiate, discover all tool pages, validate pinned
schemas and account scope, dispatch only approved method mappings, normalize
JSON-RPC/tool/provider errors, and preserve unknown mutations after cancellation.
The guide specifies ownership and acceptance; no model-bound tool registry or
assumed installed MCP server is introduced.

**Handoff gate:** fixture and real-response conformance includes unsupported mode,
missing credentials, capability isolation, page failure, HTTP-200 provider error,
and no blind create retry. Actual provider smoke is recorded separately by I02–I05.

## Sequential implementation steps

1. Review F02 read/mutation signatures and freeze adapter error categories with the four provider owners. Define injected clock, transport, secret configuration, and attempt-event hooks; add contract examples to the owned test file.
2. Implement server-private request handling with explicit timeout and total-operation budgets. Give every dispatched attempt a new providerAttemptId while preserving logicalCallId across retries. Test missing results, definitive denial, and redacted errors.
3. Implement complete pagination with page, record, response-size, and elapsed-time bounds. A failed later page or exhausted budget returns incomplete evidence; test that neither becomes an empty successful result.
4. Implement bounded read retries and Retry-After handling under one retry owner; keep automatic mutation retries disabled. Test budget exhaustion and ensure no outer loop multiplies SDK retries.
5. Implement tools/smoke/providers.ts as a disposable-account runner taking an explicit local manifest and mode. Document its future invocation through the P1-owned scripts seam, and report unavailable credentials/capabilities as unrun or failed.
6. Run the targeted transport tests and F01 build/typecheck. Have each provider owner consume the same interface example before handing off the shared branch.

## Provider attempt receipts and trusted observation boundary

Implement the transport producer seam from the [reliability plan](../06-agent-reliability-implementation.md), without opening a monitor database inside the adapter.

1. Accept injected canonical event/receipt sinks from integration. Capture logicalCallId, canonical runtimeAttemptId and distinct providerAttemptId for every dispatched tool attempt; modelAttemptId belongs only to model calls. Map legacy attemptId only through F02 compatibility and reject conflicts. Include operation/account scope, sanitized request digest, UTC start/end, process monotonic duration, page coverage and provider request ID when returned.
2. Keep transport completion, provider acknowledgement and actual application outcome separate. Persist response artifact references/digests through the injected sink; redacted events link to restricted raw receipts rather than duplicating credentials or customer text.
3. Emit planned retry/backoff delay and reason under the frozen total budget. Reads may retry only where classified safe; unknown mutations return uncertainty to B06. Incomplete pagination retains all observed pages and its failure reason.
4. Implement separate read capabilities for B07 and Q02. Trusted ingestion identifies the collector/producer from execution context and verified receipts; changing an evidence mode string must never turn imported/synthetic JSON into live provider proof.
5. Test Slack-style provider failure in HTTP 200, a missing terminal receipt, second-page failure, wall-clock adjustment, one monotonic operation budget and duplicate receipt delivery. Actual retry attempts remain visible and deduplicated by their IDs.

**Additional acceptance:** I02–I05 expose observed values plus bounded completeness/receipt metadata; Q02 can independently invoke reads without the executor's returned state. R01 injects durable sinks via B01 and Q03 consumes them; no new B01 hard dependency is added to this module branch.

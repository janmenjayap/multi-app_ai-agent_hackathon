## Sequential implementation

1. Implement authenticated input validation and durable command acceptance;
   commit accepted run identity before returning an API response. Validate CSRF
   for command routes and enforce operator/run access.
2. Initialize the application database and separate persistent checkpointer.
   Define driver state references and one active invocation per immutable incident,
   with single-process deployment assumptions explicit.
3. Schedule accepted work outside HTTP; inject graph nodes and adapters instead
   of embedding fake production behavior. Persist wait/retry/reconcile scheduling
   and restore eligible work after restart.
4. Expose F02's versioned `RunView`, cursor-event page, command/error, reconcile,
  trace/assessment and optional evaluation-summary projections. Return monotonic
  run revisions, opaque next cursors, stable event IDs, explicit availability,
  correlation IDs and redacted authorized references. Reuse monitor read/report
  semantics without letting monitoring resume business work. Show pending,
  unverified, incomplete and exhausted states accurately; absent Q05 data is
  unavailable rather than an empty or passing report.
5. Add driver/API tests in this commit: concurrent POST deduplication, disconnect,
  wait/restart, store-not-ready health, authorization/CSRF, cursor pagination and
  deduplication, stale-revision rejection, session expiry, redaction, monitor
  unavailability, and hostile client attempts to choose state, provenance or
  approval. Verify completed product with pending/failed assessment and failed
  partial effects retain distinct projections.

## Scheduling, trace, and claim integration acceptance

Implement the producer side of the [reliability plan](../06-agent-reliability-implementation.md), leaving assessment to Q03.

1. Wrap each actual graph stage in canonical start/end/error spans with parent IDs and run/evaluation identity plus runtimeAttemptId. Map legacy attemptId at the compatibility boundary only, rejecting conflicts; model and tool attempts use modelAttemptId and providerAttemptId respectively. Use B01 for state/event/job persistence; emit waiting, blocked, failed, partial, completed and stalled transitions rather than recording successful paths only.
2. Persist retry wake times, bounded deadlines and restart/causal links. Elapsed execution and human approval wait remain separable for M6; restarting must not reset the frozen attempt budget or duplicate evaluation attempts.
3. Treat each success API/UI statement as a claim with a stable ID and typed scope. Artifact-producing run completion binds the approved plan and B07 artifact/final-Slack verification. completed_no_affected_commitments uses no_affected scope with complete source, empty-selection and absence-predicate receipts; planRef is absent and no final Slack artifact is required. Replayed status reads reference the original claim rather than manufacturing repeated completed tasks.
4. Expose real assessment provenance/version, pending/unverified/exhausted status,
   evidence references and saved raw counts in the existing F02 projection. The
   status endpoint must not label an absent assessment as passing, a successful
   worker exit as independently verified, or an empty report as zero failures.
5. Add interruption tests before/after durable stage transition and a hung injected node. Observe one durable invocation, traceable unresolved stage and scheduled assessment after restart without resending protected effects. Test valid no_affected completion without a plan/Slack artifact, incomplete retrieval falsely presented as an empty selection, and conflicting legacy/runtime attempt IDs.

**Additional acceptance:** each accepted command has a durable identity; each persisted application transition has its canonical event and job. Terminal status cannot be supplied by a client or fake fixture response. Q03 receives actual lifecycle events; R01 supplies real guarded graph nodes before a product reliability claim is allowed.

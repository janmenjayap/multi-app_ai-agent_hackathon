## Sequential implementation steps

1. Implement prompt.ts with validated assessment, original supporting facts, and exactly selected commitments. State uncertainty and permitted next steps without introducing identity-selection or mutation authority.
2. Implement validate.ts for required content, claim references, unsupported dates/certainty, and attempts to change server-owned recipient/owner/action fields. Coordinate expected fields with B03 through the frozen contract.
3. Implement index.ts through A01, returning customer text and claim-to-source references with immutable first-draft evidence. Keep body generation separate from future destination IDs and approval execution.
4. Add independently labeled valid, incomplete, contradictory, changed-identity, invented-ETA, and injection fixtures in drafter.test.ts. Exercise the module using an F02 analyst fixture so A02 development can proceed independently.
5. Run targeted tests and F01 build/typecheck. When real outputs exist, review original drafts before repairs, retain correction records, and hand the draft contract to R01 and the evidence references to Q05.

## Exact drafter invocation and Gmail boundary

Follow [agent/LLM integration](../07-agent-spawning-and-llm-integration.md).
Export `draftCustomerUpdate(input: DrafterInput, ctx: AgentInvocationContext, deps)`
from **drafter/index.ts**, returning `AgentCallResult<DraftProposal>` through F02
schemas. R01's **src/server/workflow/nodes.ts** calls it in
`draft_customer_update` after a validated `IncidentAssessment` exists. Its
upstream artifact is passed as data; the drafter does not import/call A02 itself.

**The actual request path is** graph node → `draftCustomerUpdate` → A01
`invokeRole` → A01 `dispatchStructured` → `ChatOpenAI`/OpenAI Responses.
**drafter/prompt.ts** builds a fresh context from validated assessment, original
source facts, exact selected commitment facts and permitted next steps;
**drafter/validate.ts** checks claim references and attempted server-field changes
after A01 has saved the raw response. Return exact text and immutable input/output
references. B03's proposal checks run first; the auditor then receives a separately
built original-evidence/text projection. Only after a clear audit does B03 freeze
the accepted bytes into the immutable review plan.

Use `role=drafter` with the stable run/revision/role key and immutable upstream
assessment/source digest. A01 resolves optional `OPENAI_MODEL_DRAFTER` and reuses
matching committed results. No env reading, direct OpenAI import, independent
retry loop, or model regeneration while awaiting approval belongs here. One
logical invocation returns bounded draft entries keyed by exactly all selected
commitment IDs; the seeded demo happens to contain one entry. F02 freezes the
set schema and unique-entry/cardinality checks. Reject extra, duplicate, or
missing commitment IDs, and block an oversized set instead of dropping records
or introducing a per-customer spawn loop. B03 freezes each selected draft's bytes.

This role generates content only. **Gmail draft creation occurs later in B06
through I05 after exact approval**, with B07 independent readback; HubSpot tasks,
notes, GitHub comments and Slack coordination likewise use the deterministic
[external-app integration path](../08-mcp-api-and-external-app-integration.md).
Do not give the drafter provider clients, MCP tools, recipient-selection power,
or Gmail send authority. A model-produced sentence cannot establish approval.

**Additional invocation acceptance:** inspect the injected A01 request for fixed
scope and original-source references; reject invented dates, unsupported certainty,
extra recipient/owner fields and invalid citation IDs without losing raw text.
Test multiple selected commitments with exactly one returned draft per selected
ID, and invalid missing/duplicate/extra entries in the same single invocation.
R01 proves analyst → drafter ordering, zero extra drafter calls on Slack resume,
and that deterministic proposal rejection prevents auditor/plan progression.

## Sequential implementation steps

1. Use B01's same SQLite transaction for every application state transition, canonical event, and measurement enqueue. P1 owns the storage seam. Add fault tests around commit boundaries; a post-commit call to a separate MonitorStore does not establish atomicity.

2. Extend worker composition to consume that store, preserving lease fencing, bounded retries, watermarks, observation revisions, stable attempt identities, and exhausted reporting. Schedule waiting, blocked, failed, partial, completed, stalled, and no-result-start observations. Monitor outages remain pending/unverified; local ledger failure stops dispatch.

3. Implement observation-schema-v2 assessment with `evaluatorVersion: monitor-v2` through `assess.ts` and a focused `claim-verdicts.ts` seam. Preserve `monitor-v1` and `checker-v1` behavior and historical receipts. F02/Q01 define contracts; Q02's bundle is an optional input interface until integration, so absent independent evidence stays unverified rather than blocking Q03 development on the collector.

4. Bind every emitted success to a unique immutable `claimId`, channel/status event, run/attempt, claim scope, applicable plan revision, claimed predicates/artifacts, emission time, and referenced runtime verification. Distinguish artifact-summary scope (excluding its own not-yet-verified Slack write) from whole-run scope (including final Slack readback). The `no_affected` scope covers `completed_no_affected_commitments`: require complete source retrieval, deterministic complete selection, zero eligible commitments and no protected writes; it requires no planRef, approval or Slack artifact. Reading an existing persisted status again is not a new claim. Compute `prematureSuccessClaims` from emission before required verification or while writes are unresolved. A later correction does not erase this process violation.

5. Assess each claim's independent outcome as `confirmed`, `contradicted`, or `unverified`. Require scoped evidence tied to the same run and applicable plan/artifacts (or the `no_affected` selection scope) and a provider state/history window, within manifest-frozen evidence-age/settling limits, that establishes the claimed state at emission. Any contradicted required predicate contradicts the claim; confirmation requires all claimed predicates. Later drift is a separate observation, and uncertain timing remains unverified.

6. Produce `outcomeContradictedCompletionClaims` from independently contradicted unique `claimId` values only. Produce `falseCompletion` as the union of `prematureSuccessClaims` and `outcomeContradictedCompletionClaims`. Replayed events/measurements do not add claims, and a claim in both sets counts once. Keep all emitted success claims in the denominator and expose unverified claims separately. The v1 counter keeps its documented premature-only meaning; Q05 must not implement competing verdict logic.

7. Require actual matching collected/readback fields for M3 mutation-acknowledgement confirmation. An acknowledgement plus uncorroborated `matches: true` is insufficient. Missing approval, source, semantic label, or provider evidence required by the claim/scenario scope cannot produce full success from a passing checker subset. Preserve first-proposal and selected-plan semantic results separately.

8. Add application transaction/restart/lease/outage tests plus `claim-verdicts.test.ts`: acknowledged wrong recipient, absent draft, phantom Slack, premature then corrected success, repeated claim delivery, both violation kinds on one claim, correct emission followed by drift, uncertain timing, mismatched scopes, complete zero-eligible versus incomplete-source `no_affected` claims, and missing labels. Retain existing monitor/checker regressions and compare versioned v1/v2 reports explicitly.
